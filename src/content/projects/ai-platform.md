context: 公司内部多条业务线各自接入大模型，能力重复建设、技术栈不统一；智能办公、代码生成、数据分析、智能客服等场景都需要对话、生成与 Embedding 能力，但接入方式各不相同。前端之外，中台还需要服务端接口、认证授权、缓存与异步统计能力。
goals:
  - 为多条业务线提供统一的 AI 接入方式，减少重复建设。
  - 收敛对话、文生图、Embedding 等能力差异，让业务只依赖一套接口。
  - 提供会话、上下文、用量与异常的可管理能力。
  - 建立统一的认证、权限与异步统计，管理端与 API 共用一套规则。
constraints:
  - 多条业务线已有各自的模型接入，不能要求业务一次性重写。
  - 不同模型（对话、文生图、Embedding）的入参与返回结构不同。
  - 长对话与长列表同时带来渲染性能和 Token 成本压力。
  - 日志与用量统计不能阻塞对话主链路。
flow:
  - name: 业务入口
    detail: 智能办公、代码生成、数据分析、智能客服
  - name: 会话交互
    detail: 多模型对话、SSE 流式输出与历史回溯
  - name: 服务与权限
    detail: Spring Boot API、JWT + RBAC、Redis 缓存
  - name: 异步与监控
    detail: RabbitMQ 日志、Token 用量与异常监控
decisions:
  - title: 先统一服务调用层，再谈多模型接入
    problem: 对话、文生图、Embedding 的入参与返回结构不同，业务直接对接会把模型差异扩散到每个页面。
    choice: 用 TypeScript 泛型与策略模式封装 useAIService，把多模型切换、参数配置与错误处理收在一层。
    benefit: 业务侧只依赖统一接口，新增模型或调整参数不需要改业务代码。
  - title: 长列表用虚拟滚动，而不是砍掉历史
    problem: 对话历史与会话列表动辄上万条，直接渲染会带来滚动卡顿与内存压力。
    choice: 引入虚拟滚动，只渲染可视区内容并回收 DOM，消息流式输出单独做增量更新。
    benefit: 万级数据量下仍保持流畅滚动，历史记录不再因为性能被截断。
  - title: 上下文管理本质是预算问题
    problem: 多轮对话越长越贵，简单截断又会丢关键信息。
    choice: 上下文长度可配置、记忆窗口滑动、关键信息持久化，并用智能裁剪与压缩控制 Token 消耗。
    benefit: 在可控成本内尽量保持对话连贯，成本与体验可以按场景调节。
  - title: 认证与权限收在统一入口
    problem: 管理端与 API 调用都需要认证与权限，接口各自校验会重复实现，也容易出现遗漏。
    choice: 用 Spring Security + JWT 做无状态认证，按 RBAC 组织角色与权限，方法级用 @PreAuthorize 鉴权。
    benefit: 认证与权限收在一层，新增接口只需声明权限，管理端与 API 的行为保持一致。
  - title: 日志与用量离开主链路
    problem: 模型调用日志与 Token 统计写库频繁，同步处理会拖慢对话响应。
    choice: 用 RabbitMQ 异步收集调用日志与用量，开启手动 ACK 确认，配合 Redis 做幂等防重。
    benefit: 统计不阻塞对话链路，消息重复投递也不会造成重复记账。
checks:
  - 新增一个模型或能力类型，业务侧是否需要改代码？
  - 流式输出与虚拟滚动同时工作时，消息是否会错位或重复渲染？
  - 多轮对话被裁剪后，关键信息是否仍能找回？
  - 新增接口是否只需声明权限，不需要重复写认证逻辑？
  - 消息重复投递时，Token 用量是否会重复累加？
outcome: 一套中台支撑 4 类业务场景接入，前端沉淀出可复用的服务层与组件库，后端跑通认证、缓存与异步链路，前后端以容器化方式交付，业务接入成本明显降低。
